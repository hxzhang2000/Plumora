## 踩坑记录（本轮新增，后续写文档/脚本要注意）
- **Markdown 表格单元格里的 `|` 必须转义，而 pandoc 3.9 不会把 `\|` 还原成 `|`**——生成的 docx 里会留下字面反斜杠。正解：改写成文字表述（如「下卦 binary 按位或（上卦 binary 左移 3 位）」），不要用 `\|`。

## 一键启动脚本（start.bat + start.ps1）
- 用户指令：「在本项目根目录下建立一个 bat 文件（要支持 PowerShell），能自动运行后端并打开浏览器」。
- 本机环境事实：**Windows PowerShell 5.1 / zh-CN / 控制台代码页 936（GBK）**，`HKLM\...\Nls\CodePage` 的 ACP=OEMCP=936。
- **先做编码实测再定方案**（6 个变体，Python 驱动 cmd、输出重定向到文件比对原始字节）：
  - UTF-8 无 BOM `.bat` / `.cmd` → ❌ 中文被 cp936 按双字节吞掉一个字节（`开发模式` 丢字节）
  - UTF-8 **带 BOM** `.bat` / `.cmd` → ❌ BOM 不被剥离，`@echo off` 都失效（命令被回显）
  - **GBK `.bat` / `.cmd` → ✅ 字节完全一致**
- 但单文件 GBK 方案只在「控制台代码页=936」时成立，用户一开 Windows 的 UTF-8 控制台选项就再次崩。故最终采用**职责分离**：
  - 根目录 `start.bat`：**纯 ASCII**（2310 字节 / 0 个非 ASCII），只负责找 PowerShell 并转交参数，`-ExecutionPolicy Bypass` 顺带绕过执行策略；归一化 `-h/--help//?/-?` 到 `help`（否则 PowerShell 会当成未知参数报错）。
  - 根目录 `start.ps1`：全部中文逻辑，存为 **UTF-8 with BOM + CRLF**（PS 5.1 只在看到 BOM 时才按 UTF-8 解析脚本）。
  - 用法：`start.bat`（dev 5173）/ `start.bat prod`（build + preview 4173）/ `start.bat help`；可选 `-Port` / `-Timeout` / `-NoOpen`。
- **`.gitattributes` 必须锁 CRLF**：原文件只有 `* text=auto`，会把入库行尾统一成 LF，检出时若 `core.autocrlf` 不为 true 就得到 LF-only 的 `.bat` —— 而 LF-only 批处理会让 `goto` / 标签解析出错。已补 `*.bat` / `*.cmd` / `*.ps1` → `text eol=crlf`，`git check-attr` 确认生效。

### 本轮踩到的 3 个真坑（都会造成「假成功」，值得记）
1. **PowerShell 简单函数的 `[string[]]` 参数只吃一个位置参数**：`Invoke-Npm run build` 里 `build` 掉进 `$args`，实际执行的是 `npm run`（不带脚本名）→ npm 只打印脚本清单并 **exit 0**，构建被静默跳过、退出码还是 0。修法：`param([Parameter(ValueFromRemainingArguments = $true)][string[]]$NpmArgs)`。
2. **`$x = Fn ...` 会把子进程输出连同返回值一起吞进 `$x`**：`$code = Invoke-Npm run build` 里 `$code` 变成「整段 npm 日志 + 退出码」的数组，`$code -ne 0` 对数组求值恒为真 → 误判「构建失败」，同时构建日志也看不见。修法：函数内 `& npm @NpmArgs | Out-Host`，只让退出码走返回值。
3. **PS 5.1 按控制台代码页解码子进程输出**：npm/vite 输出 UTF-8，被按 936 解码 → vite 的 `✓ │ ➜` 变 `鉁� 鈹�`。修法：调用 npm 期间临时 `[Console]::OutputEncoding = UTF8`，`finally` 里还原（避免影响本脚本自己的中文）。

### 验证方式（9 条分支全绿）
用 Python `subprocess(shell=True)` 驱动 `cmd /c "start.bat ... > out.txt 2>&1"`（`shell=True` 是必须的——列表传参会被 `list2cmdline` 把引号转义坏，导致全部 rc=1 且无输出），输出**逐行 UTF-8 优先、GBK 兜底**解码。
1. `help` / `-h` / `--help` / `/?` → rc=0，帮助文本正确无乱码
2. 非法参数 → rc=2
3. 端口已有本项目服务（用当时还活着的 5183 dev server）→ rc=0 且正确跳过启动
4. 端口被别的程序占用（Python `http.server` 占 5199）→ rc=1，提示准确
5. 真实冷启动 dev 5173 → rc=0，7.2s 起好，HTTP 探测判定 OURS
6. prod 模式 → rc=0，**先删掉 `apps/web/dist` 再跑**，确认 vite build 真实执行（85 modules / dist 3 个文件被重建），避免「吃到旧产物」的假绿

### 字形来源调研（决定了技术路线，结论值得复用）
- 本机 `C:\Windows\Fonts` **无任何篆书字体**（只有 SIMLI 隶书 / STKAITI 楷体 / NotoSerifSC 等）。
- 开源篆书字体两条路都堵：**霞鹜篆书 LXGW Seal**（`dotnet010/font-LxgwSeal`，OFL 1.1）走 Unicode 18.0 小篆区块（独立于 CJK 码位），**当前仅 45 字**（福禄寿喜/干支/节气/朝代/五行/五色），**不含「观」「梅」**；**崇羲篆体**（中研院/小学堂）虽覆盖《说文》，但授权是 **CC BY-ND 3.0（禁止演绎）**，把字形轮廓烘焙进 SVG 就踩 ND。

- 篆书知识要点：小篆（秦代规范，又称玉箸篆）**线条等粗圆转、字形修长、左右对称**；视觉上的「描边感」是小篆本身的特征，不是空心字。**篆书早于简化字，故「观梅」正体写作「觀梅」**。

### 生成图 → 图标资产的管线
1. 生成：第一版是描边/斑驳风、笔画粗细不均 → 重写提示（明确「玉箸篆——线条粗细完全一致、无顿挫、无飞白」+ 指定 `#B03A2E` + 纯白底 + 明列「不要纹理/噪点/渐变/阴影/做旧/外框/印章边框/落款」）后质量明显提升。
2. **提 alpha 不用「抠白色」，用红度**：`r - (g+b)/2` 线性映射（`/120.0`）→ 抗锯齿边缘自然保留为半透明，比阈值抠图干净。
3. 裁切 → 摆入正方形画布 → potrace 矢量化 → 多尺寸导出。
4. **potracer（纯 Python potrace，pip 可装）两个 API 陷阱**（都实测确认）：
   - `Bitmap(data)` 把 **False/0 当作前景**（与直觉相反），必须传 `~mask`；
   - `CornerSegment` 用 `.c`，`BezierSegment` 用 `.c1`/`.c2`（**没有 `.c`**）。
5. **保真度自检用 IoU，且必须按 even-odd 规则栅格化**（XOR 累积奇偶性），否则孔洞被填实 → IoU 假性暴跌。最终 **IoU = 0.95874**，作为 `test:runtime` 门禁的一部分。
