## 一、版本管理体系

### 1.1 两套版本体系不要混用

| 体系 | 对象 | 形态 | 权威来源 |
| --- | --- | --- | --- |
| **产品版本** | Web 产物 + Android 安装包（**两端共用同一版本号**） | `0.1.0` / Android `versionName` + `versionCode` | 仓根 `version.json` |
| **文档版本** | 每份 md 设计文档 | `v主.次`，如 v1.4 | 该文档自己的头部字段 |

文档**独立**版本控制——不存在「文档集统一版本」，各文档各自维护、互不联动（未改动的文档不升版本）。完整规则见 [README.md](README.md) §四「文档版本控制约定」。本节其余内容只讲**产品版本**。

### 1.2 号段规范

| 项 | 规范 |
| --- | --- |
| 版本形态 | 语义化 `主版本.次版本.修订号`（X.Y.Z，三段都必须写，如 `0.1.0`） |
| Android versionName | 直接取产品版本号（`0.1.0`） |
| Android versionCode | 单调递增整数：`major*10000 + minor*100 + patch`（`0.1.0` → 100） |
| ⚠️ 约束 | 因 versionCode 按上式推导，**minor 与 patch 必须 < 100**，否则两个版本会算出同一个 code。脚本会直接拒绝 |
| 主版本 +1 | 大功能换代、数据结构破坏性变更 |
| 次版本 +1 | 新功能（如新增起卦方式、导出功能） |
| 修订号 +1 | 缺陷修复、文案微调 |

### 1.3 单一真源与派生目标

**真源只有一个**：仓根 `version.json`。其余全部是派生目标，由脚本写入，**不得手工编辑**。

```
version.json  ← 唯一权威
   │
   ├─ package.json / packages/*/package.json / apps/*/package.json   （5 个 workspace 包）
   ├─ apps/web/src/generated/version.ts                              （Web 端 TS 常量）
   ├─ apps/android/app/build.gradle.kts  → versionName / versionCode （Android，待启用）
   └─ apps/android/version.properties                                （Android 备选通道，待启用）
```

`apps/android/` 目录一旦建立，脚本会**自动接管**，无需改动脚本；目录不存在时跳过并标注「未启用」。

### 1.4 命令

| 命令 | 作用 |
| --- | --- |
| `npm run version:show` | 查看当前版本、versionCode 与全部派生目标状态 |
| `npm run version:sync` | 按真源重写全部派生目标 |
| `npm run version:check` | 校验派生目标是否与真源一致（CI 门禁，已接入 `npm run verify`） |
| `npm run version:bump:patch` / `:minor` / `:major` | 升版本 → 自动同步 → 在 CHANGELOG.md 顶部插入新条目 |
| `npm run version:bump -- <段>` | 同上，段名由参数传入 |

### 1.5 为什么需要「校验」而不只是「同步」

同步脚本本身不足以防止漂移——只要有人手工改了一个 `package.json`、或改了真源忘了跑同步，版本就会静默分叉（Web 显示 0.1.0、Android 包是 0.1.1 这种事故极难排查）。

故 `version:check` 的做法是：**对每个派生目标用同一个渲染函数重新算一遍期望内容，与磁盘逐字节比对**。写入与校验共用同一份渲染逻辑，二者不可能不一致。任一处漂移即失败并列出具体文件。

`check` 额外校验一条：**CHANGELOG.md 必须存在当前版本的条目**，防止「发了版没写变更」。

该检查已置于 `npm run verify` 的第一步，本地与 CI 都会拦住。

### 1.6 文档联动

任何**设计文档**修改必须**在同一轮内**完成三件事：改正文 → 头部「文档版本」+1 → 末尾变更日志追加一行。三者缺一即为缺陷。

产品版本变更则走 §五 的流程：`bump` → 补写 CHANGELOG.md 条目 → 提交 → 打 tag。

## 二、里程碑计划

平台推进顺序为 **Web 先行、Android 跟进**：先以 Web 端跑通全部算法与交互，沉淀共享层（`packages/`）与设计令牌，再据此实现 Android 端（见 02 文档 §一）。

### 2.1 Web 端（当前阶段）

| 里程碑 | 范围 | 出口标准 |
| --- | --- | --- |
| W0 骨架 | monorepo 搭建、共享层三包（knowledge / core / lunar）、自适应外壳、设计令牌 | `npm run verify` 全绿；农历对拍与金标准算例通过 |
| W1 MVP | 时间/数字/汉字三种起卦、排盘结果页（7 要素）、卦例保存与列表、首启声明页 | 金标准算例 A/B 通过；桌面与移动视口走查无横向滚动条 |
| W2 完善 | 随机起卦、卦例搜索/应验标记/导出 JSON+CSV、学习资料页（类象速查、64 卦速查）、深色主题 | W1 全部回归通过；新增用例（TC-W01~W12）通过 |
| W3 打磨 | 排盘图下载、性能优化、浏览器兼容性矩阵全覆盖、静态托管发布 | 07 文档 §4.1 Web 兼容性矩阵完成；无 S0/S1 遗留 |

### 2.2 Android 端（后续阶段）

| 里程碑 | 范围 | 出口标准 |
| --- | --- | --- |
| M0 骨架 | 工程搭建、导航框架、Hilt/Room/DataStore 接入、lunar-java 集成与对拍 | 空壳 App 可运行；农历对拍 200 条零差异，且与 Web 端同一份用例集结果一致 |
| M1 MVP | 时间/数字/汉字三种起卦、排盘结果页（7 要素）、卦例保存与列表、首启声明页 | 金标准算例 A/B 通过；07 文档 §六 发布准入全项满足 |

| M3 打磨 | 随机起卦、排盘图分享、拆字起卦进阶、性能优化、兼容性矩阵全覆盖 | 兼容性矩阵完成；无 S0/S1 遗留 |

## 三、分支与提交规范

| 项 | 规范 |
| --- | --- |
| 分支模型 | main（可发布）+ feature/xxx 短命分支，PR 合入 |
| 提交信息 | `type(scope): 描述`；type ∈ feat / fix / docs / refactor / test / chore。例：`feat(cast): 时间起卦支持手动输入时间（公历/农历）` |
| 版本提交 | 升版本独立成一个 commit：`chore(release): vX.Y.Z`，同轮打 tag `vX.Y.Z`。Web 与 Android 共用同一版本号，故**只有一个 tag**，不区分端 |
| 生成文件 | `apps/web/src/generated/version.ts` 等派生目标**必须入库**（否则新克隆仓库无法通过类型检查），但**不得手工编辑**——改了会被 `version:check` 拦下 |
| 文档提交 | 重要文档（README、docs/ 下全部 md）修改后可直接提交，无需逐次确认 |
| 临时文件 | 根目录杂项（导出试验、日志）一律加入 .gitignore；`node_modules/`、`dist/`、`*.tsbuildinfo`、`coverage/`、`.vite/` 已忽略。**`package-lock.json` 必须入库**（锁定依赖版本），不加入忽略列表 |
| Schema | Android 端 `app/schemas/` 变更必须与 Migration 同一 PR；Web 端 IndexedDB 结构变更须同步改 04 文档 §2.2 与 DB_VERSION |

## 四、发布流程

### 4.1 Web 端（静态托管）

1. `npm run version:bump:<段>` 升版本（自动同步全部派生目标 + 插入 CHANGELOG 条目），补写条目内容。
2. `npm run verify` 全绿 → `npm run build` 产出 `apps/web/dist`（纯静态，含 `index.html` + assets）。
3. 核对产物版本标记：`index.html` 上应有 `<html data-app-version="X.Y.Z">` 与 `<meta name="app-version">`，与真源一致。
4. 构建使用相对路径基址（`base: './'`），可直接放在任意子目录下托管，无需服务端 rewrite 配置（路由为 hash 模式）。
5. 发布前核对产物不含任何外部请求域名（NFR-02）。
6. 部署目标为任意静态托管（对象存储 / CDN / 静态站点服务）；同一份产物即国内与海外版，无渠道差异。
7. 提交并打 tag：`git tag vX.Y.Z`。Web 与 Android 共用同一版本号，tag 只有一个。

### 4.2 国内渠道（合规优先）

1. 按应用市场分类要求以「图书阅读 / 学习教育 / 传统文化」类目提交，描述文案规避「算命、占卜、预测」宣传词（见 01 文档 §五）。
2. 隐私政策页面发布到可公开访问的 URL（各市场必填）。
3. 首启声明页截图纳入审核材料，主动说明「学习研究用途」。
4. 首选渠道：vivo / OPPO / 小米 / 华为依次提交，被拒后按审核意见迭代；若多数市场拒绝，国内走官网 APK 直接分发（需签名稳定 + 官网 HTTPS）。

### 4.3 海外渠道（Google Play）

1. 应用名 Plumora，类目 Books & Reference / Lifestyle。
2. Data Safety 表单：No data collected / No data shared（与 NFR-03 一致，本地无网络权限）。
3. 目标 API 级别满足 Play 当年政策（2026 年为 targetSdk 35+）。

### 4.4 发布检查单

| # | 检查项 |
| --- | --- |
| 1 | `npm run version:check` 通过（全部派生目标与真源对齐） |
| 2 | CHANGELOG.md 已补写本次版本条目（非「（待补充）」） |
| 3 | 07 文档 §六 发布准入标准全部满足 |
| 4 | **Web 端**：生产构建成功，产物 `data-app-version` 与真源一致，无外部请求域名，桌面与移动视口走查通过 |
| 5 | **Android 端**：`versionName` / `versionCode` 与真源一致，Release 构建（R8 开启）签名包安装走查通过 |
| 6 | 首启声明页、关于页免责文案正确（关于页版本号取自生成常量，非硬编码） |
| 7 | APK 权限清单审计通过（无 INTERNET） |
| 8 | 签名 keystore 与密码不在仓库内（local.properties / 环境变量管理） |
| 9 | 已打 tag `vX.Y.Z`（Web 与 Android 共用一个 tag） |

## 五、变更日志规范

**两套版本体系对应两套变更日志，不要混用**：

| 日志 | 记录对象 | 版本体系 | 位置 | 维护方式 |
| --- | --- | --- | --- | --- |
| `CHANGELOG.md` | 产品（Web + Android 一次交付） | 产品版本 `0.1.0` | 仓根 | `version:bump` 自动插入条目，人工补写内容 |
| 各文档末尾「变更日志」 | 单份设计文档 | 文档版本 `v1.4` | 每份 md 文末 | 人工维护 |

### 5.1 CHANGELOG.md（产品）

```markdown
## [0.1.0] - 2026-09-25

**Web 端首个可用版本**

- 起卦：时间 / 数字 / 汉字笔画 / 随机 四种方式
```

要求：

1. 按版本**倒序**排列，最新在最上；顶部固定保留 `## [Unreleased]` 锚点（脚本靠它定位插入点）。
2. 标题格式固定为 `## [X.Y.Z] - YYYY-MM-DD`（`version:check` 按此串校验条目存在性）。
3. 每条只写「做了什么」，不写动机论述；多处改动用 ①②③ 编号。
4. 可用 `**工程** / **功能** / **界面** / **测试**` 粗体小标题分组，但**不强制**。
5. 升版本时脚本插入的是 `- （待补充）` 占位，**必须替换掉**才能提交（见 §4.4 第 2 条）。

### 5.2 文档变更日志（文档）

每份设计文档末尾的变更日志使用下表格式（**文档版本体系**，与产品版本号无关）：

```
| 版本 | 日期 | 变更内容 |
| --- | --- | --- |
| v1.0 | 2026-09-25 | 初版编制 |
```

写法要求：

1. 按版本**倒序**排列，最高版本在最上。
2. 每条只写「做了什么」，不写动机论述；多处改动用 ①②③ 编号。
3. 结论性变更（改口径、改数据契约）必须写明**原值 → 新值**，便于日后追溯。
4. 头部「文档版本」字段与本节最高版本号必须一致（由 `docset-selfcheck.py` 自动核查）。
