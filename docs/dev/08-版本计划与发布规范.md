## 一、版本号规范

| 项 | 规范 |
| --- | --- |
| versionName | 语义化：主版本.次版本.修订号（如 1.0.0） |
| versionCode | 单调递增整数：`major*10000 + minor*100 + patch`（1.0.0 → 10000） |
| 主版本 | 大功能换代、数据结构破坏性变更 |
| 次版本 | 新功能（如新增起卦方式、导出功能） |
| 修订号 | 缺陷修复、文案微调 |
| 文档联动 | 任何文档修改必须**在同一轮内**完成三件事：改正文 → 头部「文档版本」+1 → 末尾变更日志追加一行。三者缺一即为缺陷 |

> **⚠️ 两套版本体系不要混用**
>
> | 体系 | 对象 | 形态 | 权威来源 |
> | --- | --- | --- | --- |
> | **产品版本** | App 安装包 | `versionName` 1.0.0 / `versionCode` 10000 | `build.gradle.kts` |
> | **文档版本** | 每份 md 文档 | `v主.次`，如 v1.4 | 该文档自己的头部字段 |
>
> 文档**独立**版本控制——不存在「文档集统一版本」，各文档各自维护、互不联动（未改动的文档不升版本）。完整规则见 [README.md](README.md) §四「文档版本控制约定」。

## 三、分支与提交规范

| 项 | 规范 |
| --- | --- |
| 分支模型 | main（可发布）+ feature/xxx 短命分支，PR 合入 |
| 提交信息 | `type(scope): 描述`；type ∈ feat / fix / docs / refactor / test / chore。例：`feat(cast): 时间起卦支持农历手动修正` |

## 四、发布流程

### 4.1 国内渠道（合规优先）

1. 按应用市场分类要求以「图书阅读 / 学习教育 / 传统文化」类目提交，描述文案规避「算命、占卜、预测」宣传词（见 01 文档 §五）。
2. 隐私政策页面发布到可公开访问的 URL（各市场必填）。
3. 首启声明页截图纳入审核材料，主动说明「学习研究用途」。
4. 首选渠道：vivo / OPPO / 小米 / 华为依次提交，被拒后按审核意见迭代；若多数市场拒绝，国内走官网 APK 直接分发（需签名稳定 + 官网 HTTPS）。

### 4.2 海外渠道（Google Play）

1. 应用名 Plumora，类目 Books & Reference / Lifestyle。
2. Data Safety 表单：No data collected / No data shared（与 NFR-03 一致，本地无网络权限）。
3. 目标 API 级别满足 Play 当年政策（2026 年为 targetSdk 35+）。

### 4.3 发布检查单

| # | 检查项 |
| --- | --- |
| 1 | 版本号（versionName/versionCode）已按 §一 更新 |
| 2 | 07 文档 §六 发布准入标准全部满足 |
| 3 | Release 构建（R8 开启）签名包安装走查通过 |
| 4 | 首启声明页、关于页免责文案正确 |
| 5 | APK 权限清单审计通过（无 INTERNET） |
| 6 | 变更日志已登记（文档 + CHANGELOG） |
| 7 | 签名 keystore 与密码不在仓库内（local.properties / 环境变量管理） |

## 五、变更日志模板

每份文档与 CHANGELOG.md 统一使用（**文档版本体系**，与 §一 的产品版本号无关）：

```
| 版本 | 日期 | 变更内容 |
| --- | --- | --- |
| v1.0 | 2026-09-25 | 初版编制 |
```

写法要求：

1. 按版本**倒序**排列，最高版本在最上。
2. 每条只写「做了什么」，不写动机论述；多处改动用 ①②③ 编号。
3. 结论性变更（改口径、改数据契约）必须写明**原值 → 新值**，便于日后追溯。
4. 头部「文档版本」字段与本节最高版本号必须一致。
