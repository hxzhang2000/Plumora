## 二、快速导读

1. **第一次了解项目**：按 00 → 01 → 02 → 03 的顺序阅读。00 提供「为什么这样做」的市场依据，01—03 提供产品形态与技术骨架。
2. **准备动手写代码**：重点读 02（架构与工程结构）、03（算法规则是全 app 的灵魂）、04（存储契约）。代码在仓根的 `packages/`（共享层）与 `apps/web/`（Web 端），见 §五。
3. **做 UI**：06 是唯一依据，排盘结果页的布局约定必须严格遵守（六爻自上而下、动爻高亮）；Web 端断点见 06 文档 §6.2。
4. **做测试**：07 中预置了两组「金标准算例」（2026-08-15 午时 → 水风井；梅/花 → 火地晋），实现必须先通过这两组用例。Web 端一键跑通：`npm run verify`。

## 四、文档版本控制约定

**每份文档独立版本控制**——本体系**不存在**「文档集统一版本」。

### 4.1 为什么取消统一版本号

文档集曾使用「文档集版本」单一版本号（v1.0 → v1.4）。实测问题：任何一份文档改动后，其余 8 份版本号并不随之变化，索引里的「文档集版本」只能二选一——要么长期滞后（本次核查发现它停在 v1.0，而实际已到 v1.4），要么被迫让全部文档集体跳号。两种做法都失真。故自 v1.5 起删除该字段，改为每份文档各自维护版本号。

### 4.2 规则

| # | 规则 |
| --- | --- |
| 1 | 每份文档头部自带「文档版本」字段，**必须与该文档末尾「变更日志」表的最高版本号一致**（不一致即为缺陷） |
| 2 | 版本号形如 `v主.次`。**主版本 +1** = 结论性变更（改算法口径、改数据契约、删改章节）；**次版本 +1** = 补充说明、修正笔误、补交叉引用 |
| 3 | 每次修改该文档，**在同一轮内**完成三件事：改正文 → 头部版本 +1 → 末尾变更日志追加一行（写明改了哪几处、原值 → 新值） |
| 4 | **未改动的文档不升版本**。本轮修订中 00、02 未改动，故仍为 v1.0 |
| 5 | §一 的「当前版本」列是各文档版本的**只读镜像**，不是权威来源；权威来源永远是各文档自己的头部字段 |
| 6 | 文档间引用必须带版本号（如「见 03 文档 v1.4 §3.4」），便于日后判断引用是否已过期 |

### 4.3 变更日志写法

每条只写「做了什么」，不写动机论述；格式统一为 `| vX.Y | 日期 | 改了什么：① …；② … |`。模板见 08 文档 §五。

### 4.4 修订后的自查

改完一轮后，用**被更正的旧值**全文检索一遍，仍出现即为漏改（本轮互卦更正就是靠这招抓出 4 处残留）：

```bash
grep -rn "旧值" docs/ --include=*.md
```

更系统的做法是跑 `.workbuddy/checks/` 下的三个脚本（改完文档后建议全跑一遍）：

| 脚本 | 作用 | 期望输出 |
| --- | --- | --- |
| `docset-selfcheck.py` | 文档集自身卫生：头部版本 vs 变更日志、旧值残留、Markdown 表格列数、交叉引用目标章节是否存在 | 21 项通过 / 0 项待处理 |
| `doc-case-check.js` | 把 03/07 文档的用例逐条对拍**交付实现**（`packages/knowledge` + `packages/core` + `packages/lunar` 的 TS 源码，经 `load-delivery.cjs` 即时 bundle） | 56 pass / 0 fail |
| `kb-consistency.py` | 比对 05 文档 §3.2 速查表 / §3.5 词表 / §2.2 类目（10 列）与**交付实现**常量（经 `load-delivery.cjs`）的 64 卦数据一致性 | 无差异 |

> **对拍对象为什么是交付实现**：这三个脚本早先把 `docs/ui/build/core.js`（原型，已随定稿删除）当作「实现」，于是改 03/07 文档、或改 `packages/core` 时脚本都不报警——D-1「闰闰六月」正是这种盲区漏出来的（审查 D-4）。现只对拍交付实现（`packages/*`）。

运行方式：

```bash
python .workbuddy/checks/docset-selfcheck.py
node   .workbuddy/checks/doc-case-check.js
python .workbuddy/checks/kb-consistency.py
```

## 五、代码工程结构

```
Plumora/
├─ start.bat               # 一键启动（纯 ASCII 启动壳，转交 start.ps1）
├─ start.ps1               # 一键启动的实际逻辑（UTF-8 with BOM）
├─ version.json            # 版本号单一真源（Web + Android 共用）
├─ CHANGELOG.md            # 产品版本变更记录
├─ package.json            # npm workspaces 根（packages/*、apps/*）
├─ tsconfig.base.json      # 全仓 TS 基线
├─ scripts/version.mjs     # 版本号同步 / 校验 / 升版本脚本
├─ .github/workflows/      # CI 门禁（ci.yml）+ GitHub Pages 自动发布（deploy-pages.yml）
├─ packages/
│  ├─ knowledge/           # 卦象知识库（纯数据，零依赖）
│  ├─ core/                # 起卦 / 卦象推导 / 五行生克 / 记录模型（纯逻辑）
│  └─ lunar/               # 农历适配（Web 端 LunarProvider 实现）
├─ apps/
│  └─ web/                 # Web 应用（Vue 3 + Vite + TypeScript）
└─ docs/                   # 本目录（设计文档）
```

| 命令 | 作用 |
| --- | --- |
| `start.bat` | **一键启动**：检查环境与依赖 → 起本地服务 → 等服务就绪 → 打开默认浏览器（`start.bat prod` 先构建；`start.bat help` 看帮助） |
| `npm install` | 安装全部 workspace 依赖 |
| `npm run dev` | 启动 Web 端开发服务器 |
| `npm run build` | 生产构建（产物 `apps/web/dist`，纯静态） |
| `npm run verify` | 版本一致性 + 类型检查 + 全量单测 + 运行时冒烟 + 生产构建（提交前必跑；CI 已接入，见 `.github/workflows/ci.yml`） |
| `npm run test:runtime` | 单独跑运行时冒烟（把应用打成 IIFE 后在 jsdom 中逐路由执行） |
| `npm run version:show` | 查看当前版本与全部派生目标状态 |
| `npm run version:bump:patch` | 升版本（自动同步派生目标 + 在 CHANGELOG.md 插入条目） |
| `npm run version:check` | 校验派生目标是否与真源 `version.json` 一致 |

> **版本号只有一个真源**：仓根 `version.json`。Web 与 Android 共用同一版本号，派生目标包括 5 个 workspace 的 `package.json`、`apps/web/src/generated/version.ts`、Android `versionName`/`versionCode`。派生目标**必须入库但不得手工编辑**。完整规则见 08 文档 §一。

> **`start.bat` 为什么只是个启动壳**：`cmd.exe` 用**当前控制台代码页**解析整个批处理文件，含中文的 UTF-8 `.bat` 会被按 GBK 截成乱码命令（实测：改存 GBK 可用，但用户一旦开启 Windows 的 UTF-8 控制台选项就再次失效）。故 `start.bat` 保持**纯 ASCII**，只负责找到 PowerShell 并转交参数 —— 与代码页无关，cmd / PowerShell 下均可直接运行；全部中文逻辑放 `start.ps1`，存为 **UTF-8 with BOM**（Windows PowerShell 5.1 只在看到 BOM 时才按 UTF-8 解析脚本）。`.gitattributes` 对 `*.bat` / `*.cmd` / `*.ps1` 显式锁定 `eol=crlf`，因为 LF-only 的批处理文件会让 `goto` / 标签解析出错。

> ⚠️ **仓根 `package.json` 不设 `"type": "module"`**。各 workspace 包自带该字段；仓根若设，会把 `.workbuddy/checks/*.js` 这些既有 CommonJS 工具链一并当成 ESM，导致 §四 的自查脚本全部无法运行。详见 02 文档 §六。
